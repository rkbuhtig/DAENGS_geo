# 다음 에이전트의 작업 재개

**지금의 핵심 과제는 실제 재료가 어떤 글이 되는지 보여주는 것이다.** 수집기·슬롯·스탬프·
검증기는 그 글을 위한 수단이다. 이 문서는 이미 결정된 목적을 다시 토론하라는 지시가 아니라,
기존 작업에서 무엇을 재사용하고 어디서부터 실제 결과로 판단할지 정리한 인계다.

## 1. 현재 작업 상태

| 항목 | 상태 |
| --- | --- |
| 장면 하나를 우선하는 기획 | 사용자 채택. GEO #265 및 DEV/APP 연결 문서 병합 |
| 특별한 순간·행동 서술·참여 대상·무엇을·실제 API 기준 | 후속 사용자 결정. 이 상세 묶음에 반영 |
| 기존 슬롯·스탬프·공개 보존 구현 | 재사용할 부분이 있음. 최신 서술 계약 반영과 동일하지 않음 |
| 최신 골격에 따른 실제 지정 API 자료 분류 | 이 환경에서 호출 실패. A→B 적용 완료 아님 |
| 최신 골격에 따른 실제 LLM 품질 비교 | 아직 미검증 |
| 기존 저장 산책으로 한 문장 실험 | 실패·한계 포함 결과 보존. 개선본 전체 채택 없음 |
| Kakao 대체 실험 | 사용자 중단. 요구한 공공 API 검증으로 인정하지 않음 |
| 이번 변경 | 문서화. 새로운 API 호출·모델 호출·제품 코드 변경 아님 |

문서를 읽은 뒤 ‘기획을 이해했다’는 장문 보고를 반복하지 않는다. 작업을 재개할 때는 확보한
실제 입력과 남은 연결 문제를 짧게 밝히고, 아래 순서의 검토 가능한 결과를 만든다.

## 2. 첫 재개: 실제 지정 API의 응답부터

중단된 실험을 다시 진행하는 작업에서는 먼저 요청한 공급자를 실제 호출할 수 있는 환경을
확인한다. 인증 진단과 장면 좌표 자료 조회는 서로 다른 단계다.

1. 키를 비밀 환경에 두고, 실제 요청에서 정상 데이터 응답 또는 명시적 실패를 확인한다.
2. 좌표 A의 조회 범위를 기록하고 지정 공급자의 실제 데이터 행·필드·결측·페이지 범위를 읽는다.
3. [슬롯 문서의 분류표](03-evidence-and-slots.md)에 각 필드의 의미와 사용할 자리를 적는다.
4. 그 기준을 고정해 다른 좌표 B에도 적용한다. 바꾸면 A에 같은 기준을 다시 적용한다.
5. 공간 API가 주지 않는 참여 대상·행동·동선·환경은 실제 앱·관측 원본에서 별도로 연결한다.

원자료를 받지 못하면 그 단계는 미완료다. 다른 API·기존 스냅샷·합성 데이터로 바꾼 결과를
동일 실험이라고 부르지 않는다. 사용자가 중단한 대체 경로를 편의상 자동 재개하지 않는다.
인증키 문제인지 네트워크 문제인지 응답이 구분해 주지 않으면 원인을 확정하지 않는다.

이 단계의 결과물은 큰 수집 아키텍처가 아니라 **실제 반환값 → 의미 → 현재 좌표와의 관계 →
서술 자리/제외 사유**가 확인되는 표다. API 목록만 나열하거나 ‘공원 API이므로 공원 풍경을
쓸 수 있다’고 넘어가지 않는다.

## 3. 두 번째 재개: 같은 재료로 실제 문장을 본다

적격 근거와 중심을 고정하고 일반 장면·행동 핀의 서술을 비교한다. 장면마다 전체 세션 이해를
수행하거나 다른 장면의 초안을 입력할 필요는 없다. 원시 시간·순번·경과·전체 장면열이 HTTP
본문에 다시 들어가지 않았는지 실제 전송 자료로 확인한다.

행동 핀의 대상 필드를 새로 구현할 때까지 기다릴 필요는 없다는 사용자 지시가 있다.
실제 확인된 대상 정보로 먼저 비교하고, 없다면 그 한계를 명시한다. 설명용 가정 사례를
추가할 수는 있지만 실제 원자료로 받은 값처럼 보고하거나 공공 API 검증을 대신하지 않는다.

특별한 순간은 AI 재서술 실험에서 제외한다. 그 기록이 별도 장면으로 남고 사용자 본문과
해당 공간·환경 보조 정보가 구별되는지를 확인할 대상이다.

각 실제 생성에 다음을 함께 남긴다.

| 보여줄 것 | 왜 필요한가 |
| --- | --- |
| 장면 중심과 원문 출처 | 무엇을 기록한 장면인지, 자동 기본 문구인지 사용자 글인지 확인 |
| 원자료와 적격 근거 | 입력 부족과 잘못된 판정을 구별 |
| 실제 전송 입력·목적·프롬프트 | 모델이 어떤 과제를 받았는지 확인 |
| 모델·요청 조건·전송 본문 식별값 | 무엇을 바꾼 비교인지 재현 |
| 편집하지 않은 원문 응답 | 에이전트가 예쁘게 고친 글을 모델 성과로 보이지 않게 함 |
| 사용·생략 근거와 사실 경계 검토 | 정확성과 표현 선택을 각각 평가 |
| 개선 여부와 남은 한계 | 형식 통과를 품질 완료로 승격하지 않음 |

결과가 시설명·거리 치환문에 머무르면 개선됐다고 보고하지 않는다. 입력이 실제로 그 정도
정보만 주는지, 모델 과제가 시설 소개로 좁아졌는지, 표현 선택이 실패했는지 구별한다.
빈약한 장면을 풍부한 사건으로 꾸미는 것도 해결이 아니다.

같은 자료로 비교할 때는 무엇을 바꿨는지 분명히 한다. 입력 설명과 프롬프트를 동시에 바꾸고
한쪽만의 효과라고 주장하지 않는다. 모델 변경도 응답 실패가 많으면 품질 우열로 결론 내리지 않는다.
호출 횟수를 채우기 위한 반복보다 확인하려는 차이가 있는 비교를 우선한다.

## 4. 문장 방향이 확인된 뒤 기존 구현에 대응시킨다

다음 항목은 앞선 코드 열람에서 확인한 반영 차이다. **새 아키텍처의 확정 사양이 아니다.**
실제 구현 시작 시 해당 저장소의 최신 기준과 다시 대조하고 필요한 차이만 수정한다.

| 기존 상태·차이 | 왜 서술과 관계있는가 | 필요한 후속 판단 |
| --- | --- | --- |
| DEV 작성 입력의 중심 시각·전체 순서 | 시간 체감·연속성 단서가 실제 모델에 전달됨 | 판정 원본은 보존하고 작성 투영에서 제거·의미 재검토 |
| `background + original` 표시와 원문 접합 검증 | 전체 `body` 실험과 바로 호환되지 않음 | 일반 장면의 완성 본문, 사용자 원문, 특별한 순간을 맞는 계약으로 연결 |
| 행동 기록의 `pet_id`와 작성 입력의 생략 | 실제 행위자가 서술까지 전달되지 않을 수 있음 | 참여 목록과 핀 행위자를 구별해 필요한 표현 정보만 연결 |
| 앱의 산책 참여 대상 저장 | ‘누구와 나왔는가’ 원본은 따로 존재 | 현재 이름·역사적 이름·미지정 처리의 필요한 범위만 결정 |
| 기본 문구의 ‘속도가 느려졌다’ | 상대 저속을 변화로 표현하면 모델 전부터 사실이 강해짐 | 실제 관측 정의와 기본 문구를 함께 대조 |
| 인용·원문 보존 검사 | 사실 연결에는 필요하나 좋은 문장 자체를 증명하지 않음 | 구조·의미·서술 품질을 나눠 확인 |
| 기존 공개·수정 보호 | 생성 방식 변경 중에도 지켜야 할 사용자 경험 | 공개 뒤 늦은 결과·재진입·정책 변경이 덮지 않는지 확인 |

독립 장면이라는 의미적 결정만으로 장면마다 HTTP 요청 하나, 별도 큐, 새로운 DB, 두 writer를
필수로 만들지 않는다. 호출 묶음·병렬도·저장 형태는 품질·지연·기존 계약으로 결정한다.
특별한 순간의 LLM 우회도 원문 보호를 실현하는 유력한 방법이지 새 프레임워크 도입 사유가 아니다.

기존 code path가 목적에 맞으면 유지한다. 기획에 맞지 않는 입력·해석·접합만 작게 수정한다.
반대로 기존 호환성을 이유로 이미 철회한 ‘대표 시설 하나’나 시간순 맥락을 유지하지 않는다.

## 5. 제품 연결에서 확인할 것

PC에서 좋은 글을 한 번 만든 것과 앱의 실제 요청이 같은 자료·프롬프트로 결과를 만드는 것은
별개의 확인이다. 제품에 연결할 때는 실제 요청, 선택 근거, 공개본, 편집 경로까지 이어서 본다.

필요한 확인은 다음과 같다.

- 자유 서술 기록마다 별도 장면이 생기고 원문이 그대로 남는가?
- 위치·환경·모델 실패 때문에 사용자 기록이 사라지지 않는가?
- 행동과 기기 관측의 주체가 바뀌지 않는가?
- 일반 장면의 본문이 중복 원문 접합이나 문체 충돌 없이 표시되는가?
- 준비가 끝난 한 결과를 열며, 늦은 AI가 공개본을 바꾸지 않는가?
- 새로고침·재진입이 생성과 준비 예산을 재시작하지 않는가?
- 사용자 편집이 재생성·정책 수정·전체 일기 후속 생성보다 우선하는가?

10초는 대화에서 정한 초기 준비 예산이다. 앞선 코드 열람에서의 APP 20초, writer 15초와
섞어 하나의 숫자로 보고하지 않는다. 정확한 최신 실행값은 구현 기준에서 확인하되,
전체 준비 마감과 개별 외부 호출 제한은 서로 다른 책임임을 유지한다.

## 6. 전체 일기는 분리된 다음 단계다

전체 일기는 사용자가 채택·편집한 장면과 원본 근거, 필요하면 저장된 세션·동선의 추가 정보를
읽는 별도 생성이다. 장면 생성에 미리 그 모든 자료를 싣거나 전체 일기를 준비해야 장면을
공개할 수 있게 만들지 않는다.

장면의 생성 문장은 새로운 사실 원본이 아니다. 거기서 생략한 내용이나 선택한 표현을
전체 일기에서 독립 관측처럼 재사용하지 않는다. 세션 공백을 임의로 채우거나 사용자 편집을
다시 자동 문장으로 바꾸는 권한도 생기지 않는다.

전체 일기의 분량·화자·호출 정책·편집 UX는 이번 대화에서 완결하지 않았다. 현재 장면 서술의
필수 의존성으로 되돌려 놓지 않고 별도 결정으로 다룬다.

## 7. 다음 에이전트가 다시 만들면 안 되는 문제

| 반복하기 쉬운 접근 | 왜 이미 방향을 벗어났는가 |
| --- | --- |
| ‘모든 장면을 자연스럽게 연결하려면 전체 세션을 먼저 이해해야 한다’ | 독립 장면 우선 결정과 시간 공백 우려를 되돌림 |
| ‘시설 하나와 거리만 말하면 안전하다’ | 사실 제약을 고정 문장 구성으로 바꿔 서술 역할을 없앰 |
| ‘특별한 순간도 원문 뒤에 배경을 붙이면 보존된다’ | 사용자 본문에 AI가 관여하지 않는 최신 예외를 무시함 |
| ‘누가 했는지 스키마부터 완성해야 문장을 볼 수 있다’ | 사용자가 서술 전략을 미루지 말라고 명시함 |
| ‘핀과 동선을 모두 어떻게로 묶는다’ | 사용자가 무엇을을 별도로 복구한 이유를 놓침 |
| ‘공원 API이므로 연못 옆길을 쓰면 된다’ | 실제 반환 필드와 현재 좌표 관계를 확인하지 않은 가정 |
| ‘요청 API가 안 되니 다른 실제 API면 충분하다’ | 사용자가 그 대체 실험을 중단시킴 |
| ‘3/1/1과 250m를 구현했으니 슬롯 기획을 완성했다’ | 실행값과 유효 조건의 목적을 혼동함 |
| ‘인용 검사 통과, 테스트 통과, 앱 적용이면 품질도 완료다’ | 각 검증이 답하는 질문이 다름 |
| ‘문서 이해 보고를 더 만들고 문장은 나중에 본다’ | 사용자가 가장 답답해한 작업 순서의 반복 |

## 8. 아직 열려 있는 선택

원칙이 미결이라는 뜻이 아니라, 원칙 안에서 실제 결과로 정할 선택들이다.

- 행동 서술의 구체적 말투·화자 정책. 가까운 거리감은 확정됐지만 모든 글의 고정 1인칭은 아니다.
- 각 API의 실제 반환 필드와 좌표 관계를 새 골격에 적용하는 방법.
- 의미를 잃지 않는 현재 장면 동선 투영의 범위.
- 특별한 순간의 보조 공간·환경 표시 형식과 사진 전용 장면의 세부 정책.
- 반려견 이름·행위자를 실제 작성 입력까지 연결하는 최소 변경.
- 일반 장면 전체 본문과 원문·편집·인용 계약의 구체적 변경.
- 모델·프롬프트·분량·호출 묶음·준비 예산의 실제 비교 결과.

미결을 이유로 확정 원칙부터 다시 설계하지 않는다. 답이 필요한 선택이 어느 실제 문장이나
제품 동작을 바꾸는지 설명하고 그 부분의 결과로 판단한다.
