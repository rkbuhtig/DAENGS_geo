# HOW 조각을 기록 중심 스탬프에 조립하기

같은 합성 산책에서 사진·메모 위치만 바꿔 **동일한 움직임이 언제 중심이고 언제 맥락인지** 비교했다.
HOW 7조각을 3개 스탬프 후보로 조립했고, 기록이 있는 지점에서는 해당 기록이 중심이 됐다.
이는 룰 기반 구성 실험이다. LLM 호출·최종 장면 선정·서술 품질 평가는 하지 않았다.

## 구현 경계

`StampTool("record_how", source, policy)`가 새 입력 경로다.
[how_stamps.py](../../../../scripts/spikes/diary_storyboard/how_stamps.py)는
기존 기록 스탬프와 [HOW 추출기](how-materials.md)를 연결한다.
`query/resolve/anchor/dump/load`와 기존 `stamp_storyboard`의 ID 선택·작성 계약을 그대로 쓴다.
기존 `record_envelopes` 경로와 `archived_v1` 보존 응답은 유지한다. 운영 app·Dev·App 코드는 바꾸지 않았다.

입력은 `{route, records, attachments}`다. route는 원본 관측, records는 기록·봉투 스냅샷,
attachments는 정확한 기록 버전과 `client_seq`의 명시적 연결이다.
이번 어댑터는 같은 세션·합성 여부와 관측 참조·좌표·시각 일치를 검사한다.
시간이나 위치가 다른 기록을 가장 가까운 GPS에 임의로 붙이지 않는다.
사진 파일은 없고 합성 사진 기록의 참조만 있다. 기존의 다른 좌표를 가진 기록 fixture를 이 동선에 가져다 붙이지 않았다.

연결이 없거나 해당 관측이 HOW 품질 검사에서 제외되면 기록 스탬프는 보존하되 HOW를 붙이지 않는다.
서로 다른 canonical chain뿐 아니라 더 엄격한 HOW 정확도·속도 검사로 끊어진 run도 연결하지 않는다.
과거 행동·공간 봉투를 이어받을 때도 이 새 경로에서는 동일한 run의 명시적 연결을 요구한다.

## 중심과 슬롯 정책

| 판단 | 이번 실험 규칙 |
|---|---|
| 움직임 중심 후보 | 국소 체류·큰 방향 전환·직전 구간 되짚기 |
| 직선 구간 | 단독 스탬프를 만들지 않고 연결 맥락으로만 사용 |
| 방향 반전 + 되짚기 | 같은 관측 꼭짓점이면 함께 구성 |
| 체류와 다른 HOW | 다른 HOW 대표점이 체류 관측 범위에 있고 15m 이내일 때 함께 구성 |
| 묶음 확대 | 모든 조각이 서로 조건을 충족해야 함. 연쇄 겹침만으로 묶음을 늘리지 않음 |
| 기록 + 회전 | 동일한 run, 대표 꼭짓점 ±20초·15m 이내 |
| 기록 + 체류/되짚기 | 해당 관측 support 안에 기록의 정확한 관측이 있을 때 |
| 여러 중심에 연결 가능 | 연결 가능한 묶음 중 대표 관측과의 시간차가 가장 작은 묶음 하나 |
| 연결 직선 슬롯 | 중심 꼭짓점과 닿거나 체류 support와 겹치는 직선 최대 2개 |
| 중심 없는 기록 | 기록 관측을 포함하는 직선만 맥락으로 제공 가능 |

묶음의 대표를 고르는 내부 순서는 되짚기 → 체류 → 회전이다. 서로 겹치는 축 중 대표 참조를 고르는 규칙이며
산책 전체의 서사적 중요도 순위가 아니다. 직선 슬롯은 중심과 가까운 source sequence 끝점을 우선한다.
이 문턱과 순위는 합성 실험용이며 실측 보정이나 사용자 검증을 거치지 않았다.

현재 HOW 슬롯은 **산책 종료 후 스탬프별로 준비하는 제한된 맥락 슬롯**이다.
실시간 LRU·TTL 스트림을 구현한 것이 아니다. 중심 조각은 보호하고, 직선 맥락의 채택/용량 제외는 audit에 남긴다.
원본 HOW 카탈로그는 그대로 유지한다. 슬롯에서 제외했다고 이동이 끝났거나 기록이 삭제됐다는 뜻이 아니다.
기존 공간·행동·환경 슬롯의 정책과 HOW 구성 정책은 별도다.

사용자 기록은 현재 한 기록당 필수 스탬프 하나다. 여러 기록이 같은 HOW를 공유할 수 있다.
해당 HOW 묶음의 독립 후보는 중복 생성하지 않는다. 기록을 합쳐 삭제하거나 맥락 전용 기록으로 바꾸지 않는다.
기록이 없는 HOW 묶음은 선택 가능한 스탬프다. 최종 장면 수·의미에 따른 생략은 아직 결정하지 않는다.
필수 기록이 기존 카드 한도를 초과하면 기존 계약처럼 명시적 분할을 요구하며 자동 삭제하지 않는다.

## 시간은 세 가지를 구별한다

1. **기록 시각 / 대표 관측 시각**: 지도 핀이 참조하는 원본. 회전의 실제 시작 시각을 확정한 값이 아니다.
2. **HOW support**: 계산이 참조한 관측 구간. 각 조각의 범위를 그대로 유지한다.
3. **available_at**: 연결된 HOW support가 모두 끝나 판정 재료가 갖춰지는 시각.

이번 산책의 1:30 사진에는 0:00–5:30 관측으로 판정한 회전이 붙는다.
그렇다고 사진이 5분 30초짜리 행동으로 바뀌지는 않는다. 스탬프 전체에 합쳐진 사건 지속시간을 만들지 않는다.
사진은 1:30 한 지점에 있고, 회전·앞뒤 직선 각각의 원본 support가 따로 남는다.
체류와 회전이 공존할 때도 시각이 겹친다는 이유로 ‘머문 후 회전했다’라는 순서를 만들지 않는다.

모델용 딕셔너리에는 `center`에 대응하는 기록/태그와 `how[]`의
`material_ref`, `role`, `relation`, `kind`, `status`, `subject`, `support`, `metrics`, `quality`를 보낸다.
role은 `focus/cofocus/focus_context/shape_context`다. 원본 좌표 배열은 투영하지 않는다.
한 번의 긴 프롬프트로 이 관계들을 추론하게 하지 않고 시스템이 관계와 사용 범위를 고정한다.

## 같은 동선 비교 결과

공통 동선은 직진 → 우회전 → 중간 체류 → 같은 방향으로 진행 → 직전 구간 되짚기다.
HOW는 직선 3, 회전 2, 체류 1, 되짚기 1로 총 7조각이다.

| 조건 | 사용자 기록 | 스탬프 후보 | 필수 후보 | 확인한 동작 |
|---|---:|---:|---:|---|
| 회전 지점 사진 | 1 | 3 | 1 | 사진 중심 + 회전/직선 맥락 |
| 체류 중 메모 | 1 | 3 | 1 | 메모 중심 + 체류/직선 맥락 |
| 되짚기 시작 근처 메모 | 1 | 3 | 1 | 메모에 방향 반전과 되짚기를 함께 연결 |
| 기록 없음 | 0 | 3 | 0 | 회전·체류·되짚기 중심 후보 |
| 기록 세 개 함께 | 3 | 3 | 3 | 기록 모두 보존, 같은 HOW의 별도 카드 중복 없음 |
| 회전보다 1분 앞선 사진 | 1 | 4 | 1 | 긴 회전 support 안에 있어도 회전에 연결하지 않음 |
| GPS 공백 앞뒤 기록 | 2 | 2 | 2 | 각 run의 직선만 연결, 회전/이전 행동 연결 없음 |

3개라는 수를 강제하지 않았다. 먼 사진 조건에서 4개가 되는 이유는 사진이 별도로 남기 때문이다.
모든 조건에서 저장 후 재계산한 책과 투영이 일치했다. 선택 요청 JSON은 준비만 했으며 발송하지 않았다.

## 실행과 검증

```powershell
uv run python -m scripts.spikes.diary_storyboard.how_stamp_demo --out ../diary-lab/how-stamps-01
uv run pytest tests/spikes/diary_storyboard/test_how_stamps.py tests/spikes/diary_storyboard/test_how_materials.py tests/spikes/diary_storyboard/test_stamp_tool.py -q
```

출력의 `index.html`에서 조건과 스탬프를 선택한다. HOW 조각을 누르면 해당 원본 support만 강조한다.
`{case}/source.json`, `stamp_book.json`, `view.json`, `selection_request.json`과 `report.json`을 보존한다.
새 출력 디렉터리만 허용한다. 페이지의 SVG·마커는 좌표에서 자동 생성하며 지도 API나 이미지 생성을 쓰지 않는다.

첫 표적 검사 57개 중 56개가 통과했고 재생 검사 1개가 실패했다.
HOW 정책 기본값이 정수로 계산되다가 JSON 복원 후 float가 되면서 동일한 문턱값의 근거 해시가 달라졌다.
정책 기본값 검증을 켜 계산 시점부터 수치 형식을 고정했다.
그 뒤 영향받은 조립 19개 + HOW 18개를 재실행해 **37개 모두 통과**했다.
기존 스탬프 검사 20개는 첫 실행에서 통과했으며 후속 수정의 대상이 아니었다.
변경 Python 5파일의 Ruff도 통과했다. 전체 저장소·실기기·실제 모델 검증은 수행하지 않았다.

기존 HOW 실험의 원본 출력은 덮어쓰지 않았다. 기본값 형식 수정으로 일부 HOW 참조 해시는 달라질 수 있어
이전 카탈로그의 참조를 새 카탈로그에 혼합하지 않는다. 검출 수치의 의미와 이전 실제 LLM 응답은 바꾸지 않았다.

## 작업하면서 드러난 다음 문제

**관측 조각과 읽는 단위를 분리하는 것은 동작한다.** 직선·회전·되짚기를 모두 별도 카드로 만들 필요가 없고,
같은 재료도 사진이나 메모가 생기면 그 기록의 맥락이 될 수 있다.

다만 회전 판정의 앞뒤 단순화 구간이 길면 support도 길다. 이번에는 사진 시각을 보호했지만
LLM에 주는 이동 맥락까지 충분히 짧아졌다는 증거는 아니다. 다음에는 원본 support를 보존한 채
중심 주변에서 사용할 짧은 관계·표현용 요약 범위를 따로 정할지 검토할 필요가 있다.
그 범위를 실제 행동 지속시간으로 취급해서는 안 된다.

WHERE와 HOW를 함께 배치하는 정책, 여러 사용자 기록의 편집상 묶기, 긴 산책의 후보 생략,
원좌표가 사라지기 전의 운영 저장, 실제 관측과 사진 시각의 연결 어댑터는 남아 있다.
구성을 고정한 뒤 짧은 작성 요청으로 LLM을 비교하는 단계도 아직 실행하지 않았다.

후속 [작성용 조각 투영](how-writing.md)에서 원본 support를 보존하고, 고정 스탬프의 HOW 정의·참조를
짧은 작성 딕셔너리로 분리했다. 전달 전후 크기·원본 연결을 확인했으며 실제 모델 비교는 아직 실행하지 않았다.
