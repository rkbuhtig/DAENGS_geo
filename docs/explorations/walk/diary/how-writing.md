# 같은 스탬프의 전체 입력과 짧은 작성 재료 비교

후속 [실제 Gemini 작성 비교](../../../research/2026-09-08-how-writing-gemini.md)를 완료했다.
아래는 호출 전에 확정한 투영 정책과 오프라인 결과를 보존한 기록이다.

[HOW 스탬프 조립](how-stamps.md)의 후보·중심·연결을 고정하고 **작성 입력의 형태만** 바꿨다.
원본 근거를 줄이거나 새 장면을 고르는 단계가 아니다. 새 모델 호출은 0회이며 문장 품질·토큰·비용을 측정하지 않았다.

## 경계와 사용법

[writing_projection.py](../../../../scripts/spikes/diary_storyboard/writing_projection.py)의
`prepare_comparison(tool, selected)`가 기존 `writing_request`와 같은 선택·순서·필수 기록·용량 검사를 사용한다.
기존 요청을 `baseline_input`, 새 요청을 `compact_input`으로 보존한다. 프롬프트와 응답 스키마는 동일하다.
선택은 호출자가 전달하며 투영기가 추가·생략하지 않는다. 실험 화면에서는 기존 후보 전체를 고정했다.

`StampTool.project`, 원본 책, 스탬프 버전, 지도 anchor, 기존 카드 계약은 수정하지 않았다.
새 투영의 버전은 스탬프 버전과 별도로 관리한다. 기존 `accept_writing`과 `render`로 응답·원본 위치를 연결할 수 있다.
이번에는 합성 응답으로 연결 계약만 검사했다. HTTP 실행·새 프롬프트·의미 검증기를 추가하지 않았다.

## 무엇을 남기고 무엇을 보관 쪽으로 옮겼나

| 정보 | 작성 입력 | 로컬 보존 |
|---|---|---|
| 기록 원문·사진 참조·기록 시각·시각 기준 | 그대로 | 원본 기록 |
| 스탬프 ID·순서, HOW 역할·관계 | 그대로 | 정확한 스탬프 버전 |
| 과거 행동·WHERE 봉투 투영 | 그대로, 이번 압축 범위 밖 | 기존 봉투·관계 |
| HOW 정의 | 한 요청의 딕셔너리에 한 번씩 | 원본 카탈로그 |
| HOW 연결 | `h1` 같은 짧은 참조 | 참조와 원본 ID·버전의 대응표 |
| 회전 | 좌/우/반전, 대표 꼭짓점 기준과 시각 미확정 | 전체 판정 구간·각도·앞뒤 길이 |
| 체류 | 관측 구간 길이 + 행동 지속시간이 아니라는 기준 | 전체 구간·표본·체류 계산 수치 |
| 되짚기 | 직전 구간과의 관계, 반환 구간의 변위 | 이전/현재 관측 참조·비교 허용 범위 |
| 직선 | 대략적인 직선 형태, 기존 연결 역할·관계 | 구간 길이·편차·허용 오차 |
| 정확도 | p50과 정확도 누락 관측 수 | 전체 품질 지표 |
| 연속 동선 scope | 원본 chain/run 식별자 유지, 서로 다른 run의 연속성은 미확정 | 전체 support |
| 원본 support·판정 완료 시각 | 전달하지 않음 | 원본 책에서 조회 |

HOW의 `status=candidate`, `subject=recording_device`, 합성 실험에서만 보정한 상태도 유지한다.
시간차는 기존 관계를 그대로 쓴다. `record_minus_vertex_s`는 회전 꼭짓점 관측과 기록의 차이이며
회전 후 실제로 몇 초가 흘렀다는 확정값이 아니다. `record_offset_s`도 관측 support 시작과의 차이다.
관측 구간이 겹친다고 ‘머문 다음 회전했다’라는 순서를 추가하지 않는다.

원본 GPS는 기존 작성 투영에도 없었다. 이번 절감은 GPS를 처음 제거한 효과가 아니라
**긴 HOW support·진단 수치·반복 정의·버전 해시를 작성 입력에서 옮긴 효과**다.

정확히 같은 HOW ID와 버전만 중복 제거한다. 두 직선이 같은 종류나 같은 요약값을 가진다고 합치지 않는다.
GPS 공백 양쪽의 직선은 별개의 정의다. `route_run`에 원본 chain/run 쌍을 남기며,
`cross_route_run_continuity=not_established`를 함께 전달한다. 별칭이 다르다는 사실만으로 공백을 이해하도록 맡기지 않는다. 동일한 조각을 여러 스탬프에서 사용하는 연결도 유지한다.
`h1` 같은 별칭은 요청 안에서만 유효하며 다른 산책/요청의 동일한 별칭과 공유하지 않는다.

## 투영 예시

사진 근처 회전의 필요한 필드만 발췌하면 다음과 같다. 아래는 전체 요청이 아니다.

```json
{
  "how_dictionary": {
    "h1": {
      "kind": "turn",
      "direction": "right",
      "time_basis": "route_vertex_not_exact_turn_time"
    }
  },
  "how": [{
    "use": "h1",
    "role": "focus_context",
    "relation": {
      "type": "record_near_turn_vertex",
      "basis": "observed_vertex",
      "record_minus_vertex_s": 0,
      "turn_occurrence_time": "not_resolved"
    }
  }]
}
```

전체 입력에는 사진 기록·정확한 시각, 후보 상태·주체·정확도·HOW 한계가 함께 있다.
사진 기록을 0:00–5:30의 행동으로 확대하지 않으면서 회전 근거의 원본 구간은 로컬에서 확인할 수 있다.
현재는 작성 요청 하나에 딕셔너리와 고정 스탬프들을 함께 전달하는 구조다.
스탬프별로 호출을 나누면 각 요청에 필요한 정의를 다시 준비해야 하므로 현재의 공유 절감률을 그대로 적용할 수 없다.

## 보존과 검산

`manifest`는 원본 scope 버전, 선택된 스탬프 버전, HOW 별칭 대응표, 양쪽 입력·프롬프트·응답 스키마 해시와 정책을 가진다.
`projection_version`은 이 명세의 해시다. 이것들은 로컬 검산 자료이며 LLM 입력에 통째로 보내지 않는다.

`verify_comparison(tool, saved)`는 같은 참조로 다시 준비해 전체 결과를 비교한다.
`resolve_how(tool, saved, alias)`는 이 검산 후 정확한 원본 HOW를 돌려준다.
입력·별칭·원본 버전·통계가 바뀌면 저장된 비교를 그대로 재사용하지 못한다.
모델이 요청해 근거를 추가 조회하는 실행 루프는 구현하지 않았다.

## 7조건 결과

공백을 제거한 UTF-8 **입력 JSON 바이트 수**다. 양쪽에 같은 인코딩 방식을 적용했고 공통 프롬프트·응답 스키마는 포함하지 않았다.
모델 토크나이저나 실제 API 사용량을 측정한 수치가 아니다.

| 조건 | 기존 B | 짧은 입력 B | 감소 | HOW 정의 전→후 | 유지한 연결 |
|---|---:|---:|---:|---:|---:|
| 회전 지점 사진 | 7,463 | 3,475 | 53.44% | 9→7 | 9 |
| 체류 중 메모 | 7,438 | 3,450 | 53.62% | 9→7 | 9 |
| 되짚기 시작 근처 메모 | 7,514 | 3,526 | 53.07% | 9→7 | 9 |
| 사용자 기록 없음 | 7,353 | 3,365 | 54.24% | 9→7 | 9 |
| 기록 세 개 함께 | 8,261 | 4,273 | 48.28% | 9→7 | 9 |
| 회전보다 이른 사진 | 8,499 | 3,737 | 56.03% | 10→7 | 10 |
| GPS 공백 | 2,317 | 1,427 | 38.41% | 2→2 | 2 |

구성은 기존과 같은 3/3/3/3/3/4/2개 스탬프다. ‘연결 9개 유지’는 HOW 정의를 9번 반복할 필요가 없다는 뜻이다.
기록 세 개 조건은 보존하는 원문·이전 행동 관계가 더 많아 절감률이 낮다. 그것들을 이번에 임의로 줄이지 않았다.

## 실행과 화면

```powershell
uv run python -m scripts.spikes.diary_storyboard.how_stamp_demo --writing-comparison --out ../diary-lab/how-writing-01
uv run pytest tests/spikes/diary_storyboard/test_writing_projection.py -q
```

새 출력 디렉터리만 허용한다. `--writing-comparison`이 없으면 기존 HOW 조립 화면을 만든다.
기존 `source.json`, `stamp_book.json`, `view.json`, 준비된 선택 요청을 보존하면서
각 조건의 `writing_comparison.json`에 작성 전후·프롬프트·스키마·명세·통계를 추가한다. 모든 요청은 `not_sent`다.

`index.html`에서 조건과 스탬프를 고르면 나란히 비교할 수 있다.
‘선택 스탬프’는 관련 딕셔너리와 기록의 발췌이고, ‘전체 전달 JSON’이 실제 전달 예정 입력이다.
상단 절감률은 언제나 고정된 전체 요청 기준이다. HOW 참조를 누르면 원본 구간·지도·전체 수치를 확인한다.

화면 점검 중 브라우저가 `8.0`을 `8`로 재직렬화해 본문 바이트와 상단 수치가 달라지는 문제를 발견했다.
원래 인코더로 만든 JSON 문자열과 크기를 함께 표시하도록 수정했다. 투영 입력과 절감률은 변하지 않았다.
표시 자료는 별도 `writing_display`이고 LLM 입력/원본 버전의 일부가 아니다.

처음 투영 검사 17개가 통과했고, 표시 형식 회귀를 추가한 뒤 **18개 모두 통과**했다.
단절 정보를 작성 입력에도 남기도록 보강한 뒤 영향받은 공백·바이트·표시·산출물 검사 4개를 다시 실행해 통과했다.
변경 Python 3파일의 Ruff도 통과했다. 원문·시각·방향, 체류 시간의 기준, 순서 미확정,
정확도 누락, GPS 공백, 필수 기록/선택, 낡은 별칭·변조, 원본 책 재생, 기존 카드 anchor와 연결을 검사했다.
공용 app/Dev/App 코드와 기존 스탬프 생성기는 바꾸지 않았으며 전체 저장소 테스트는 수행하지 않았다.

## 이번 결과가 말해주는 것과 다음 단계

같은 구성을 더 작은 작성 입력으로 표현하고 원본까지 추적할 수 있었다.
어떤 기록이나 후보가 더 중요한지를 새로 판단한 실험은 아니다.
각도·길이 같은 진단 수치를 생략해 문장이 좋아지는지, 짧은 참조가 모델에게 충분히 쉬운지는 아직 모른다.
짧은 정의가 같아 보이는 서로 다른 직선을 모델이 혼동하는지도 실제 작성에서 확인해야 한다.

다음은 이 구성을 그대로 두고 양쪽 입력의 작성 결과를 비교하는 단계다.
원문 기록 보존, 방향·시간 관계의 정확성, 반복, 근거 없는 장소·목적 추가를 분리해서 봐야 한다.
토큰과 비용은 그때 실제 사용량으로 기록한다.
