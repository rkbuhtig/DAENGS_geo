# 산책 세션의 연속성과 붓의 연속성은 다르다 — 중단·재개·체류 초안

이 문서는 산책 중 시설 체류, 수동 일시정지, GPS 중단, 앱 프로세스 종료가 생겼을 때
**무엇을 하나의 산책으로 볼지**와, 그 기록을 영역 칠하기에 어떻게 넘길지를 정리한다.
아직 채택된 결정이 아니다. 실제 기기 UX와 데이터가 나오기 전에 상태 수·자동 복구 정책·체류
표현을 확정하지 않는다.

핵심 가설은 하나다.

> **산책 세션의 연속성과 GPS/붓의 연속성은 분리한다.**
>
> GPS가 끊겨도 하나의 산책일 수 있다. 그러나 관측이 끊긴 곳을 붓으로 이어 칠하지 않는다.

`territory-paint.md`의 "산책 한 번 = 셀로판 한 장"과 충돌하지 않는다. 한 장의 셀로판 안에
서로 떨어진 여러 개의 칠해진 구간이 있을 수 있다. 빈 구간은 **모르는 구간**이지 연결할
구간이 아니다.

## 왜 필요한가

산책은 러닝처럼 끝까지 연속 기록되는 운동만이 아니다.

```
집 ──────── 반려동물 카페
               │
               │ 40분 휴식 / GPS OFF
               │
               └──────── 집
```

사용자에게는 한 번의 외출일 수 있지만, 고정밀 GPS를 40분 계속 켜둘 이유는 없다. 반대로
GPS를 껐다는 구현 사정 때문에 산책을 두 개로 쪼개면 사용자 의미가 저장 방식에 끌려간다.

또 이 서비스에서 GPS는 단순 경로 표시가 아니라 **영역을 칠하는 증거**다. 누락된 후반 경로는
아쉽지만, 관측하지 않은 직선이나 추정 경로를 칠하는 것은 더 나쁘다. 따라서 복구의 목표는
"완벽한 선 만들기"가 아니라 **관측한 것과 관측하지 않은 것을 섞지 않는 것**이다.

## 세 층을 분리한다

### 1. `WalkSession` — 사용자 관점의 한 번의 산책/외출

세션 경계는 GPS 연결 여부가 아니라 사용자의 의도로 정한다.

- 사용자가 산책을 시작하면 열린다
- 기록을 잠시 멈춰도 세션은 살아 있을 수 있다
- 사용자가 종료하거나, 나중에 미완료 세션을 종료 처리하면 닫힌다
- 한 세션 안에 GPS 연속 구간이 여러 개 있을 수 있다

따라서 "GPS가 꺼짐 = 산책 종료"는 아니다.

### 2. 기록 구간 / chain — 연속해서 관측한 위치 증거

GPS가 실제로 연속 관측된 범위다. 현재 raw fix의 `chain_index`가 이 경계를 전달하는 축이다.

다음 사건은 chain을 끊는다.

- 사용자가 추적을 일시 중단
- 앱/서비스가 죽어 위치 수집이 중단
- 명시적 pause/resume
- 서버가 이미 gap/jump로 판정하는 관측 단절

중요한 규칙:

> **chain A의 마지막 점과 chain B의 첫 점 사이에는 선을 만들지 않는다.**

그 사이를 실제로 걸었을 수도 있고, 차를 탔을 수도 있고, 같은 장소에 있었을 수도 있다.
증거가 없으면 공간도 칠하지 않는다.

### 3. Paint stroke / Cellophane — 관측된 구간에서만 만든 영역

붓은 유효한 기록 구간에서만 나온다.

```
WalkSession #17
├─ chain 0  집 → 카페       → paint stroke A
├─ [GPS OFF / unknown]      → 아무것도 칠하지 않음
└─ chain 1  카페 → 집       → paint stroke B

Cellophane #17
= stroke A + 빈 구간 + stroke B
```

셀로판의 의미는 "한 산책에서 관측된 공간"이지 "시작점과 끝점 사이를 모두 지나갔다"가 아니다.

## 상태 초안 — `pause`보다 `suspend`의 의미가 중요하다

제품 표면의 이름은 나중에 정해도 되지만, 의미는 다음 셋이면 출발할 수 있다.

```
RECORDING
  고정밀 위치 기록 중

SUSPENDED
  세션은 살아 있음
  고정밀 위치 기록은 멈춤

FINISHED
  세션 종료
```

시설에서 쉬는 사용자는 `SUSPENDED`로 들어갈 수 있다. 이 상태의 목적은 "산책을 종료하지 않고
GPS 비용을 내린다"다.

재개는 우선 **사용자 명시 동작**을 기본으로 본다. 자동 재개를 위해 저전력 위치·지오펜스·활동
인식 등을 계속 돌리면 "GPS를 쉬게 하려고 suspend했다"는 목적과 충돌할 수 있다. 사용감이
필요하면 먼저 foreground notification이나 앱 재진입 시 **재개 알림**으로 보조한다.

자동 재개는 실제 기기에서 누락률과 배터리 비용을 본 뒤 별도 실험한다.

## 앱/서비스가 죽은 경우 — 세션과 기록 중단을 같은 사건으로 만들지 않는다

예기치 않은 프로세스 종료는 사용자가 산책을 끝냈다는 뜻이 아니다.

```
chain 0 ───── X process death

          관측 없음

앱 재진입
  ├─ Resume  → 새 chain 시작
  ├─ Finish  → 관측된 것만으로 종료
  └─ Discard → 세션 삭제 정책으로 이동
```

복구 시 과거 gap을 새 위치까지 보간하지 않는다. 재개하면 새 chain을 만든다.

`START_NOT_STICKY`를 유지할지, 미완료 세션을 얼마나 오래 살려둘지, 재부팅 뒤에도 복구 표면을
보일지는 아직 정하지 않는다. 이들은 **세션 의미**가 아니라 운영/UX 정책이다.

## 누락 허용 원칙

영역 칠하기에서는 다음 비대칭을 의도적으로 받아들인다.

- 실제로 걸었지만 기록을 놓침 → coverage가 덜 칠해진다
- 기록이 없는데 추정해서 연결함 → 걷지 않은 공간이 사용자의 경험으로 저장될 수 있다

두 오류의 비용이 다르다.

> **놓친 영역은 허용한다. 관측하지 않은 영역을 경험으로 만들지는 않는다.**

이 원칙은 GPS gap, 프로세스 죽음, suspend/resume 모두에 동일하게 적용한다.

## "진함"도 하나의 뜻으로 쓰지 않는다

`territory-paint`는 현재 산책별 `Cellophane`을 쌓아 `occupancy`·`walks`·`peak`를 질의한다.
여기에 실제 지도 표현을 붙일 때 **두 종류의 진함을 같은 시각 채널로 합치지 않는 것**을
검토한다.

### A. 반복 통과 — 셀로판이 겹쳐서 진해짐

이 축은 "얼마나 자주 이 공간을 경험했나"에 가깝다.

```
1회   ░
3회   ▒
10회  ▓
20회  █
```

`walks`와 산책별 `peak` 문턱이 이 질문의 재료다. 여러 산책이 같은 영역을 반복해서 칠한 결과다.

### B. 체류 — 싸인펜을 한 자리에 대고 있어 스며듦

이 축은 "한 번의 산책 안에서 이곳에 얼마나 머물렀나"에 가깝다.

반복 통과와 같은 색 농도로 표현하면 다음 둘을 구별할 수 없다.

- 같은 길을 20번 통과
- 한 번 갔지만 벤치에서 30분 체류

따라서 렌더링 단계에서는 체류를 별도 채널로 두는 안을 우선 검토한다. 예:

- 반복 통과: 셀로판 겹침 / opacity / saturation
- 체류: 중심 halo, 번짐, 질감, 별도 contour

구체 색·효과는 아직 결정하지 않는다. 저장값에 색을 굽히지 않는다.

## 체류는 raw GPS point 밀도로 만들지 않는다

정지한 폰의 GPS는 한 점에 고정되지 않고 주변으로 흔들린다. raw fix를 그대로 "한 점에 오래
대고 있는 싸인펜"으로 누적하면 실제 벤치 하나가 수십 미터 얼룩으로 번질 수 있다.

따라서 체류 시각화는 raw point 개수보다 **정지/체류 사건**을 재료로 삼는 쪽이 안전하다.
현재 파이프라인의 `MotionEventOccurrence`처럼 시간 구간과 위치 불확실성을 가진 파생이 후보가
될 수 있다. 정확한 dwell 계약은 별도 실험으로 정한다.

### 특히 `SUSPENDED` 시간은 관측된 체류가 아니다

사용자가 카페 앞에서 GPS를 끄고 50분 뒤 다시 켰다고 해서, 시스템이 그 50분 동안 같은
좌표에 있었다고 관측한 것은 아니다.

따라서 다음을 구분해야 한다.

- **observed dwell**: GPS가 켜진 상태에서 정지 사건으로 관측
- **suspended interval**: 특정 시각에 추적을 끄고 나중에 재개했다는 사실
- **declared visit**: 사용자가 시설 방문/휴식을 명시적으로 확인한 경우 — 향후 후보

`suspended interval`을 자동으로 `observed dwell`로 승격하지 않는다. 시설 체류를 제품 기능으로
쓰고 싶다면 시설 선택/사용자 확인 등 별도 근거를 붙여야 한다.

## 시간도 둘일 수 있다

세션을 GPS와 분리하면 "산책 시간"이라는 숫자도 한 뜻이 아니다.

- `elapsed/session duration`: 시작부터 종료까지의 외출 시간
- `tracked/active duration`: 실제 위치 증거가 있는 기록 시간
- `suspended duration`: 추적을 의도적으로 내린 시간

어떤 값을 사용자에게 "산책 시간"이라고 보여줄지는 아직 정하지 않는다. 다만 하나의 숫자로
미리 접으면 나중에 시설 체류와 실제 보행 시간을 다시 분리할 수 없다.

## 지금 확정하지 않는 것

- 몇 시간/며칠 뒤 열린 세션을 자동 만료할지
- 재부팅 후 미완료 세션을 자동 복구할지
- 이동 감지로 resume reminder를 띄울지
- `SUSPENDED`를 제품 UI에서 "일시정지", "나중에 재개" 등 무엇이라 부를지
- observed dwell의 공간 반경·최소 시간
- 체류와 반복 통과의 실제 색/불투명도/질감 정책
- 체류를 `Cellophane` 내부 값으로 저장할지, 별도 파생 레이어로 둘지
- 종료 후 업로드 재시도/WorkManager 정책 — 세션 의미가 정해진 뒤 별도 운영 결정

## 구현으로 넘어가기 전 확인할 것

1. 실제 산책에서 시설/벤치/신호 대기 등 정지 시간 분포를 수집한다.
2. `pause → GPS OFF → resume`가 배터리와 재개 누락률에 실제로 이득인지 기기에서 잰다.
3. 같은 세션의 여러 chain을 `territory-paint`에 넣었을 때 gap이 절대 연결되지 않는 테스트를 둔다.
4. 정지 GPS jitter를 raw accumulation과 event-based dwell로 각각 그려 비교한다.
5. 반복 통과와 장기 체류를 같은 색 축으로 그렸을 때 얼마나 혼동되는지 시각 샘플로 비교한다.

이 다섯 결과가 나오기 전에는 상태를 더 늘리거나 자동 재개를 복잡하게 만들지 않는다.
