# 공간 일기 제작 계획 — 장면을 검토하고 한 편의 일기로 확정하기

이 문서는 **공간 일기 작업을 다시 시작할 때 먼저 읽는 기획·진행 기준**이다.
2026-09-05부터 이어진 대화의 결정 이유와 구현 상태를 모았다. 앞으로 달라지는 계획과
상태는 이 문서를 갱신하고, 실험 결과는 날짜가 있는 research 문서로 남긴다.
`working-skeleton`은 아래 일부 흐름이 구현됐다는 뜻이며 완성된 일기 제품을 뜻하지 않는다.

현재는 **실제 산책 → 규칙 기반 장면 분석 → 앱 검토·편집·검토 완료본 저장**까지 구현·머지됐다.
운영 DB 적용 여부와 실기기 흐름은 확인이 남아 있다. **AI 일기 생성은 미구현**이다.
사용자는 당장 후속 실행을 진행하기 어려워, 구현을 더하기 전에 재개 기준을 남기기로 했다.

## 1. 만들려는 경험과 이 구조를 선택한 이유

산책 중에는 보호자가 관찰한 행동과 기억할 순간을 가볍게 남긴다. 종료 후 시스템이 필요한
위치의 환경과 산책 기록을 읽어 시간순 장면을 구성한다. 보호자가 그 구성을 확인하고
고친 뒤, 원할 때 확정한 재료로 한 편의 AI 일기를 만든다. 핀을 누르지 않은 산책도
시작·이동·끝의 흐름과 확인 가능한 배경을 돌려준다.

논의는 다음 순서로 바뀌었다. 이 이유를 잊고 버튼이나 생성 기능부터 다시 설계하지 않는다.

1. **핀의 역할:** 일기 화면에 놓는 마커에서, 특정 시각·위치의 관찰을 보태고 종료 후
   읽을 환경을 고르는 근거로 구체화했다. 기록의 입력 의미와 최종 출력 선택은 분리한다.
2. **행동 어휘:** 탐색·교류·특별한 순간에는 관찰과 해석이 섞여 있었다. 킁킁·배설·짖기를
   관찰 입력으로 정하고 특별한 순간은 자유 메모로 둔다. 개인화 정책은 먼저 확정하지 않는다.
3. **핀 없는 산책:** 행동 입력에만 의존하면 평범한 산책에 결과가 없어진다. 관측 가능한
   경로에 최소 조회 목표를 두고 행동·이동 변화·빈 거리 보충을 조합하는 초안을 구현했다.
4. **변화와 일상의 균형:** “익숙한 공간이에요”만으로는 전달할 정보가 적다. 평소와 다른
   정보가 있으면 활용하되, 차이만 수집해서 산책 전체의 흐름을 잃지 않는다.
5. **공간과 시간의 분리:** 여러 산책의 속도를 비교하는 것과 셀로판을 겹쳐 공간 이용을
   읽는 것은 다른 질문이다. 공간 이력을 모든 장면의 최상위 우선순위로 확정하지 않았다.
6. **사람의 개입 위치:** 전체 흐름을 LLM이 읽고 각 구간에 이야기를 배치한 뒤 바로 일기까지
   만들면, 작은 수정도 전체 재생성을 부르기 쉽다. **스토리보드 검토 완료와 AI 일기 생성
   요청 사이에 사람의 결정**을 둔다. 검토 완료 자체는 LLM 호출이 아니다.

## 2. 이번 초안에서 유지할 결정

| 항목 | 현재 기준 |
|---|---|
| 행동 버튼 | **킁킁 / 배설 / 짖기**. 킁킁의 저장 코드는 `sniffing` |
| 배설 | 소변·대변을 나누지 않고 관찰 기록으로만 받음. 마킹 의도는 추정하지 않음 |
| 특별한 순간 | 시각·가능한 위치를 가진 자유 메모. 행동 목록 커스텀 기능은 아직 없음 |
| 다른 개와 인사 | 기본 버튼에서 제외. 만남 대비 실제 입력 기회가 적을 것이라는 사용자 판단 |
| 기록 수정·삭제 | 원본 기록에 적용. 현재 분석과 기록 집계에서 제외/갱신해야 함 |
| 이번 구성에서 숨김 | 출력 선택. 원본 행동이나 프로필 근거를 삭제하지 않음 |
| 산책 기록 프로필 | 기록 수·기록이 남은 산책 수·근거를 전달하는 계약부터 둠. 성향·성격 정책은 미정 |
| 횟수의 의미 | 버튼 입력은 기록된 장면. 실제 행동 횟수나 행동이 없었다는 증거로 쓰지 않음 |
| 환경 | 관찰에 배경을 더함. 근처 시설이 있다는 사실로 방문·행동 원인·감정을 만들지 않음 |
| 자동 선정 지점 | 환경 조회/이동 관측 후보. 새 사용자 행동 핀이나 행동 기록 수로 세지 않음 |
| 사용자 편집 | 분석 원본과 별도 보관. 원본 변경 시 사용자 문구를 남기고 재확인을 요구 |
| 검토 완료 | 포함한 장면과 근거의 마지막 완료본 하나를 저장. 전체 판본 이력은 아직 없음 |
| 과거 입력 호환 | 기존 행동 어휘를 보존할 필요 없다는 사용자 결정으로 초기 전환은 이미 수행함. 향후 실제 기록 삭제에 대한 포괄 허용은 아님 |

단일 반려견은 기본 귀속, 다견 행동 기록은 대상 선택을 지원한다. 특별한 순간은 산책 전체
메모다. 프로필 계약의 클라이언트는 있으나 **프로필 표시 화면은 아직 연결하지 않았다**.
사진 저장은 앱의 별도 기능이며 현재 행동 동기화·장면 분석·AI 입력에 자동 포함된다고 보지 않는다.

## 3. 전체 흐름과 시스템 경계

```text
GPS 관측 + 행동 기록 + 메모
  → 업로드 / GPS finalize / 기록 동기화
  → 유효 구간·공백과 기록에서 조회 지점 선택
  → 선택한 위치의 환경 조회
  → 출처·revision이 있는 시간순 장면 후보
  → 보호자가 문구 편집 / 숨김 / 원본 정정
  → 최신 구성을 검토 완료하고 사본 저장
  ── 여기까지 구현, 운영 실사용 확인은 남음 ──
  → 사용자가 AI 일기 생성 요청
  → 확정한 사본으로 일기 초안 생성
  → 일기 열람·수정·보관 [후속 설계/구현]
```

현재 장면 선택과 문구 구성은 **규칙 기반**이다. “전체 흐름을 먼저 읽고 장면마다 서사적
역할을 배치하는 LLM 편집”은 아직 후보이며, 위 장면 후보와 사람 검토 사이에 필요성이
확인되면 넣을 수 있다. 이를 현재 구현된 스토리보드 생성과 혼동하지 않는다.
첫 AI 일기를 만드는 데 이 추가 LLM 단계를 반드시 선행시킬지는 미정이다.

- **geo:** GPS lab, 선택·장면 규칙, fixture, 계약, 가설과 평가의 원본.
  규칙은 `app/features/storyboard/`에 두고 좁은 GPS 수집 코어에 일기 의미를 넣지 않는다.
- **dev:** 운영 인증·원본·DB·세대 관리·환경 조회 API. geo lab 프로세스를 운영 중계하지 않는다.
- **app:** 입력·동기화·장면 검토 UI·사용자 편집과 완료본. 현재 사용자 검토본은 로컬 Room 저장이며
  서버 분석 저장과 다르다. **검토본의 다른 기기 복원/서버 동기화는 미구현**이다.

같은 ID의 장면 원본이 바뀌면 편집을 유지하고 확인을 요구한다. 삭제된 원본에 붙었던 사용자
문구는 보존하지만 현재 구성에서 제외한다. 새 분석이 도착했다고 이미 저장한 완료본을
자동 덮어쓰지 않는다. 분석 원본, 편집 중 구성, 완료본, 앞으로 만들 일기를 구별한다.

## 4. 조회 지점의 현재 초안과 공간 이력의 자리

**최소 목표 4구간 / 분리 거리 100m / 최장 빈 거리 300m / 최대 조회 지점 8개**다.
이는 시설 수나 최종 장면 수, “반드시 특별한 사건 4개”를 보장하는 값이 아니다.
근거가 부족하면 목표 미달과 사유를 남긴다.

1. 액션 핀을 먼저 선택한다. 가까운 후보는 근거를 함께 묶되 원본 기록을 합쳐 지우지 않는다.
2. 과거 비교가 가능하면 이전 산책 대비 지속적인 이동 변화로 부족한 목표를 채운다.
3. 현재 세션 기준의 지속적인 속도 변화로 채운다.
4. 남은 경로 중 가장 긴 빈 구간의 중앙에 가까운 유효 관측점으로 보충한다.
   목표 달성 후에도 300m를 넘는 빈 구간은 예산 안에서 보충한다.

앞부분에 핀이 몰렸어도 전체 경로를 처음부터 고정 간격으로 다시 찍지 않고 **남은 공백**을
읽는다. 누적 관측 이동거리를 쓰며 GPS 단절을 가로질러 이동·정지나 좌표를 지어내지 않는다.
선정 지점의 주변 조회 범위가 그 경로 구간 전체 환경을 증명하지는 않는다.

현재 dev의 과거 비교는 같은 회원·같은 **한 마리만 동행한 최근 과거 산책 3개**의
관측 이동속도 중앙값을 사용하며 모두 유효해야 한다. 장소별 개인화가 아니다.
현재 선택 규칙의 이동 변화 문턱은 기준의 0.5배 미만/1.75배 초과가 20초 이상 지속하는 값이며,
제품 검증을 마친 최적 문턱으로 취급하지 않는다. 자세한 계산은
[우선순위 실험 기록](../../research/2026-09-05-priority-context-draft.md)을 따른다.

| 재료 | 답할 수 있는 질문 | 이번 일기에서의 상태 |
|---|---|---|
| 한 세션의 시간·속도·공백 | 이번 산책 어디서 이동 양상이 바뀌었나 | 현재 후보 선정에 사용 |
| 여러 세션의 속도 기준 | 과거 기록의 이동 기준과 어떻게 다른가 | 좁은 대리 지표를 사용 |
| 싸인펜 | 한 산책의 관측 시간이 공간에 어떻게 배분됐나 | geo의 공간장 계산 재료 존재. 행동 원인 판정기는 아님 |
| 셀로판·통계층 | 선택한 여러 산책에서 어디를 얼마나 이용했나 | geo 계산·저장·질의 재료 존재. 현재 live 일기에는 미연결 |
| 행동별 개인화 | 비교 가능한 상황에서 어떤 관찰 기록이 반복되나 | 정책 미정. 산책 기록 프로필 계약과 구별 |

공간 이력은 장면에 보탤 맥락 후보다. “익숙한 곳”이라는 문장을 필수로 만들거나 현재
`profile_change` 선택 이유를 셀로판 기반 행동 판정이라고 부르지 않는다. 장소별 비교를
추가하려면 비교 기간·분모·관측 품질·삭제 반영을 먼저 정하고 현재 방식과 가치를 비교한다.
배경은 [싸인펜·셀로판·통계층](cellophane-statistical-layer.md),
[미시 판정 탐색](micro-judgment.md)에 남아 있다.

운영 환경 조회는 기존 Place 인덱스의 **여가 시설·카페·음식점**, 반경 250m, 종류당 최대 3곳이다.
최대 8지점·동시 4조회·개별 3초·전체 10초 제한을 둔다. lab의 공원·하천·상가 자료와
공급 범위가 같지 않다. 조회 실패나 결과 없음은 미확인으로 남기고 산책 기록은 제공한다.

  이번 작업에서 직접 적용하지 않았고 자동 배포는 이 SQL을 실행하지 않는다.

- 운영 Place 자료가 실제 산책 위치에서 얼마나 유용한 배경을 제공하는지 평가하지 못했다.
- AI 생성, 일기 판본, 검토본 서버 동기화, 개인화 프로필 UI/정책은 구현하지 않았다.

배포 성공을 새 테이블 적용이나 실사용 완료의 증거로 바꾸지 않는다. 재개 시에는 상태가
변경됐을 수 있으므로 다시 조회한다. 최신 기술 계약은
[geo 실데이터 이식](../../contracts/walk-storyboard-live.md),
[dev live 문서](https://github.com/SAJOYO/DAENGS_dev/blob/dev/docs/walk-storyboard-live.md),
[app live 문서](https://github.com/SAJOYO/DAENGS_APP/blob/dev/docs/walk-storyboard-live.md)를 본다.

### A. 실제 한 사이클 확인 — 실행 환경을 확보하면 먼저

운영 DB 테이블·배포·Place 연결을 읽어서 확인하고 필요한 운영 변경 범위를 정한다.
새 APK를 실기기에 설치해 아래 사례를 실제 API와 함께 확인한다. DB 적용 작업은 운영
소유 저장소인 dev에서 진행한다. 지금 이 문서 작성이 운영 변경을 실행한 것은 아니다.

| 사례 | 완료 기준 |
|---|---|
| 핀 없는 정상 산책 | 흐름과 자동 후보가 보이며, 목표 미달이면 사유를 표시 |
| 핀이 앞쪽에 몰린 산책 | 행동 근거를 유지하고 남은 경로를 예산 안에서 보충 |
| 짧은 산책·GPS 공백·위치 없는 메모 | 가짜 위치나 이동을 만들지 않고 기록·공백을 보존 |
| 원본 수정·삭제 / 분석 중 재수정 | 오래된 응답을 채택하지 않고 최신 구성에서 확인 요구 |
| 환경 실패·응답 유실 | 산책 원본 보존, 미확인 표시, 재시도로 복구 |
| 장면 숨김·문구 편집·검토 완료 | 원본과 편집의 구별, 완료본 고정, 재분석 후 편집 보존 |

**산출물:** 테스트한 앱/서버 커밋, 사례별 결과, 화면 관찰, 실패 원인을 날짜가 있는
research 기록으로 남긴다. 인증정보·정확한 개인 경로를 PR 첨부물에 넣지 않는다.

### B. 확정 스토리보드 → AI 일기 계약 — 구현 전 먼저 결정

다음은 **제안하는 설계 작업**이며 확정 API나 저장 스키마가 아니다.

- 입력: 검토 완료본의 장면·사용자 문구·근거와 그 버전을 명시한다. 생성 중 바뀔 수 있는
  현재 분석을 다시 읽어서 입력을 바꾸지 않는다. 좌표·사진 등 전달 범위는 따로 결정한다.
- 실행: 사용자가 생성할 때만 호출한다. 반복 탭·타임아웃·재시도의 중복 비용을 어떻게
  막을지와 동일 완료본의 기존 결과를 재사용할 기준을 정한다.
- 출력: 일기가 어느 완료본에서 나왔는지 추적 가능하게 한다. 생성 초안과 이후 사용자가
  고친 본문을 구별하고, 근거 없는 방문·행동·감정·인과를 추가하지 않는 평가를 둔다.
- 변경: 완료본 수정 후 기존 일기를 그대로 둘지, 오래된 근거 안내를 할지, 사용자가 새로
  생성할 때 어떻게 교체할지 정한다. 부분 수정마다 전체 호출을 강제하지 않는다.
- 수명: 검토본/일기의 서버 보관, 다른 기기 복원, 판본 개수, 산책·핀 삭제가 생성된 일기에
  미치는 영향을 정한다. 현재 로컬 마지막 완료본 정책만으로 미래 일기 수명을 추정하지 않는다.
- 형식: 짧은 글 한 편을 먼저 시험할지, 장면별 문단을 유지할지 결정한다. 모델·프롬프트·
  길이·비용 상한은 아직 미정이다.

**산출물:** 요청/응답·상태·오류·버전/삭제 경계를 담은 계약 초안과 동일 재료의 출력 예시.
사용자가 검토할 수 있는 계약을 만든 뒤 dev 생성 기능과 app 요청/열람을 연결한다.

### C. 첫 AI 일기 구현과 평가

B의 계약에 따라 완료본 선택 → 명시적 생성 → 결과 열람·편집을 한 사이클로 만든다.
자동 생성 재시도와 사용자의 재생성 요청을 구별하고 원본 기록·검토본은 보존한다.

**완료 기준:** 같은 완료본을 입력으로 재현/추적할 수 있고, 핀 없음·삭제·환경 미확인 사례도
허구 없이 읽힌다. 생성 실패가 검토 완료본을 손상시키지 않는다. 비용·지연과 사용자 수정량을
함께 기록해 규칙 문구 대비 무엇이 나아졌는지 판단한다. 최종 글의 형식은 B에서 결정한다.

### D. 흐름 편집과 추가 맥락 실험 — 필요한 효과부터 검증

현재 규칙 장면 → 사람이 검토 → 일기 생성만으로 흐름이 부족한지 먼저 본다.
부족하다면 **전체 흐름 읽기 → 장면의 역할 배정 → 사람 검토**라는 LLM 편집을 비교한다.
지역 전환·공간 이력·사진·게임 성과는 독립 근거가 있는 경우의 선택 재료로 검토한다.
모든 재료를 첫 일기의 선행 의존성으로 만들지 않는다.

**완료 기준:** 동일 산책에서 시작·중간·종료가 더 잘 이해되는지, 차이만 과장하지 않는지,
수정 부담과 호출 비용이 늘어난 만큼 가치가 있는지 사례로 비교한다. 셀로판을 추가한다면
속도 비교만으로는 얻지 못한 공간 정보가 무엇인지 명시한다.

### E. 산책 기록 프로필의 다음 단계 — 별도 정책을 정한 뒤

먼저 현재 계약의 기록 수·산책 수·근거를 어디에 보여줄지 정한다. 그다음 공간별 반복과
상황별 경향의 분모·귀속·편향·정정/삭제 반영을 실험한다. “사회성/성격 점수”나 다음 산책
추천을 단순 기록 수에서 바로 만들지 않는다. 이 작업은 한 세션 일기 완성의 필수 조건이 아니다.

## 7. 서버·기기 없이 이어갈 수 있는 준비

운영 확인이 어려운 동안은 새로운 구현보다 **고정 재료로 출력의 가치와 계약을 검토**할 수 있다.

- `tests/fixtures/storyboard/`의 다섯 사례로 핀 없음·핀 쏠림·공백·정지·정정/삭제를 비교한다.
  합성 GPS와 실제 공공자료 캐시의 결합이며 실사용 기록이 아니다.
- [GPS/산책 기록 lab](../../../scripts/spikes/walk_record_lab/README.md)에서 기존 경로를
  재사용해 선택 기준을 바꿔본다. Docker 없이 실행하며 API 재조회 없이 캐시로 비교할 수 있다.
- 규칙 그대로 / 전체 흐름만 편집 / 확정 뒤 일기 작성의 예시를 같은 입력으로 만든다.
  생성기를 실험할 때 합성 정답을 입력에 섞지 않고 관측 bundle만 사용한다.
- 사람의 문구 수정·숨김·원본 삭제별로 “어떤 산출물이 바뀌고 어떤 호출이 필요한가”를
  표로 정리해 B의 계약에서 수정 비용을 검토한다.

현재 PC의 키·캐시는 저장소 밖 `C:/Users/Administrator/daengs-walk-record-lab/`에 두었다.
PC 초기화/이동 뒤 이 폴더가 남는다고 가정하지 않는다. 비밀키를 문서나 fixture에 복사하지
않고 별도 안전한 경로로 복구한다. 키 없이도 저장소의 고정 JSON을 검토할 수 있다.
로컬 PostgreSQL 통합 테스트는 별도 도구/격리 DB가 필요하며 lab 자체의 실행 조건은 아니다.
