# 지도 목적별 표시 정책

status: **working-skeleton**

target owner: **app repository**

current implementation: 이 저장소의 Android 실험 셸

## 왜 별도 정책층인가

한 지도 SDK를 장소 검색·산책·점령 게임이 공유해도, 각 화면이 답해야 하는 질문은 다르다.
시설 저장소나 점령 저장소가 직접 마커를 켜고 끄기 시작하면 기능 간 우선순위를 알 수 없고,
화면 전환 뒤 이전 기능의 오버레이가 남을 수 있다. 반대로 provider가 기능 의미를 알면 Naver 외
다른 지도 구현으로 옮기기 어렵다.

따라서 기능은 후보 데이터를 소유하고, `map/shell`은 현재 `MapPurpose`를 하나만 선택해 그 목적에
허용된 레이어로 `MapScene`을 합성한다. provider는 완성된 scene을 그리며, 배경지도의 표현 강도만
provider API로 번역한다.

## 현재 표시 계약

| 목적 | 현재 위치 | 시설 검색 결과 | 산책 동선 | 점령지 | 배경지도 |
|---|---:|---:|---:|---:|---|
| 장소 검색 | 표시 | 표시 | 숨김 | 숨김 | 시설·도로 탐색에 필요한 문맥 유지 |
| 산책 | 표시 | 숨김 | 사용자 설정에 따라 표시 | 숨김 | 길 찾기 문맥을 유지하되 심볼 약화 |
| 점령 | 표시 | 숨김 | 진행 중인 산책만 표시 | 표시 | 길·건물은 유지하고 심볼을 더 약화 |

점령 지도도 실제 위치를 찾아가야 하므로 단색 게임판으로 만들지 않는다. 도로와 건물 윤곽은 남기고,
앱이 올린 시설 마커는 완전히 제거한다. Naver 기본지도 자체의 POI는 별도 데이터 레이어가 아니므로
현재 working skeleton에서는 크기만 낮춘다. 완전 제거가 필요한지는 실제 단말 가독성을 본 뒤 provider
스타일 실험으로 결정한다.

## 코드 경계

- `MapViewModel`: 현재 목적을 배타적인 상태로 소유한다. 장소 검색 진입은 `PLACE_SEARCH`, 산책 탭은
  `WALK`, 점령 토글은 `WALK`와 `TERRITORY` 사이를 전환한다.
- `MapScenePolicy`: 목적과 사용자 선호를 visible layer allow-list로 바꾸고, 금지 레이어를 빈 값으로
  만든다. 렌더러가 visibility flag를 실수로 무시해도 데이터가 새지 않는다.
- `NaverMapSurface`: 목적별 `BaseMapStyle`을 Naver SDK 설정으로 번역한다. 기능 데이터나 제품 상태를
  조회하지 않는다.
- 장소·산책·점령 기능: 각각 검색 결과, 경로, 점령지 후보를 계속 소유한다. 표시 여부는 소유하지 않는다.

## 이 실험이 아직 하지 않는 것

- 점령지 조회 API를 Android에 연결하거나 viewport 단위 로딩 정책을 정하지 않는다.
- 10m 인증 반경, 세션 비정상 종료, 사진 VLM 대기 상태와 점령 확정 정책을 정하지 않는다.
- Naver 기본지도 심볼을 시설 DB 결과와 같은 것으로 취급하지 않는다.
- 이 저장소 구현을 최종 앱 구조로 확정하지 않는다. 앱 저장소로 옮길 때 위 표시 계약과 순수 정책
  테스트를 먼저 이식하고, UI 및 provider adapter는 그 앱 구조에 맞춘다.

## 다음 검증

실제 단말에서 장소 검색·산책·점령을 왕복하며 다음을 확인한다.

1. 시설 검색 마커가 산책·점령 화면에 남지 않는가.
2. 점령지를 찾아갈 만큼 도로와 건물 문맥이 남는가.
3. 점령지 수가 늘어도 scene 합성과 overlay 교체가 프레임을 막지 않는가.
4. 검증 뒤 점령지 네트워크 로딩은 `MapPurpose.TERRITORY`와 viewport를 함께 조건으로 삼는다.
