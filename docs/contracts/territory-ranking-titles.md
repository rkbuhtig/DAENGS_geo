# 동네 순위·칭호 — 정책과 저장·API 계약 초안

선행 작업은 [산책·점령 세션/통계 기반](../explorations/walk/activity-statistics-skeleton.md)이다.
산책 확정 분석과 점령 보유 이력을 먼저 기록하고, 여기의 비교·칭호는 버전과 근거가 있는 통계를
읽는 후속 소비자로 구현한다. 점수에서 사실 통계를 역산하지 않는다.

**이 문서의 동네/칭호 계약은 새로 작성한 검토안이며 구현·합의·운영 채택된 정책이 아니다.**
이미 있는 기능과 추가할 기능을 분리하고, DEV/APP 작업자가 구현 전에 닫아야 할 결정을 남긴다.
전체 구현 경위와 이관 순서는 [게임 인수인계](../explorations/walk/territory-game-handoff.md)를 읽는다.

문서의 `제안 v0`는 구체적인 검토 기준이다. 사용자가 수치·조건을 승인했다는 뜻이 아니며,
채택할 때 결정 기록과 계약 버전을 만들고 테스트를 작성한다. 이 문서를 추가하는 PR은
칭호 테이블·수여 함수·랭킹 API·APP 화면을 추가하지 않는다.

## 1. 현재 재사용 가능한 기반과 없는 것

| 현재 Geo에 있음 | 의미/한계 |
|---|---|
| `Score`의 bonus/holding_units/current_count/scoring_count/peak/claims/takeovers/held_site_ms | 성적 계산 근거. 지역 가입·칭호 자격·공개 동의를 표현하지 않음 |
| `plan_finalization` | 한 시즌 계정을 총점 순으로 정렬. 동일 점수는 공동 순위 `1,1,3` |
| `FinalStanding`, `territory_policy_result` | 종료 당시 Score·정확한 총점·순위 보존 |
| `territory_policy_season.scope_id` | 활성 시즌 중복을 막는 범위 키. 경계 도형/지역명/실제 동네 판정 없음 |
| `create_season(..., site_ids)` | 명시한 장소 집합으로 시즌 생성. 실제 주소에서 동네를 고르지 않음 |
| PostgreSQL 종료 재실행/영수증 재생 | 수여 원장의 참고 기반. 칭호 중복 지급을 이미 막는다는 뜻은 아님 |

현재 없는 것은 **동네 경계 버전, 장소-동네 매핑, 랭킹 조회 snapshot/API, 칭호 정의·지급 원장·
수여 작업·취소/복원·대표 선택·공개 프로필·APP 화면**이다. 성적에 `rank=1`이 저장돼도
칭호를 받았다고 표시하면 안 된다.

## 2. 동네와 참가 범위 — 제안 v0

### 2.1 동네 식별

동네는 관리되는 장소 집합으로 시작하는 안을 제안한다. 행정동을 그대로 쓸지, 게임용 경계를
쓸지는 미정이다. 선택 후에는 `scope_id`, 표시 이름, `boundary_version`, 장소 목록의 원본과
갱신 근거를 저장한다. 화면에서 고른 이름이나 실시간 GPS 좌표만으로 영구 귀속하지 않는다.

- 한 장소는 같은 시기의 게임에서 하나의 scope에만 속한다. 경계선 위 장소도 서버의 고정 매핑으로 결정한다.
- 시즌 시작 때 장소-동네 매핑과 경계 버전을 고정한다. 시즌 중 지도 데이터를 다시 적재해도 과거 성적 범위를 바꾸지 않는다.
- 새로 추가한 장소·경계 수정은 다음 시즌부터 반영하는 것을 기본 제안으로 둔다. 긴급 제거·점수 보정 절차는 별도 결정한다.
- 장소 ID 안정성은 기존 territory site 계약을 따른다. 지도 표시 이름 변경과 site ID 변경을 혼동하지 않는다.

### 2.2 시즌과 여러 동네 활동

현재 `(season_id, pet_id)`가 계정 키이므로 **동네별·기간별 별도 season ID**를 두는 안을 제안한다.
같은 강아지가 A·B 동네에서 활동하면 두 계정에 각각 해당 장소의 점수가 쌓인다. 동시 보유 배율도
각 시즌/동네 내부 보유 수로 계산한다. 두 동네 점수를 합한 전국 순위·전역 배율은 v0 범위 밖이다.

앱에서 동네를 선택하는 것은 조회 대상을 바꾸는 행위다. 서버는 점령한 장소의 매핑으로 점수를
귀속하므로, 사용자가 조회 동네를 바꿔 이미 획득한 점수를 이동시킬 수 없다. 별도 거주지 인증이나
집 주소 수집은 이 제안의 참가 조건이 아니다. 다른 동네 방문 참가를 허용할지는 아래 결정표에서 닫는다.

한 산책이 두 시즌/동네를 지날 수 있으므로 전체 산책에 시즌 하나를 고정하지 않는다. **시도별**
시즌 귀속을 저장한다. 시즌 경계의 새로운 시도와 기존 사진 callback도 원래 시도를 기준으로 나눈다.
이 동작은 현재 DEV #260에 구현되지 않았으며 후속 schema/접수 검증이 필요하다.

특히 동일 산책·동일 장소의 시즌 경계 재도전은 기존 DEV/APP의 산책/장소 유일성 키와 충돌한다.
시즌을 포함한 키로 확장할지 새 산책을 요구할지도 D-03에서 닫는다. 원래 사진 callback과 새 시즌
시도를 분리하는 migration/대기열 호환 검증이 끝나기 전에는 지원한다고 표시하지 않는다.

## 3. 순위 계산과 조회 — 제안 v0

### 3.1 계산 대상·동점

- 경쟁 단위는 회원이 아닌 강아지다. 여러 강아지 산책에서는 해당 장소 시도의 대표견에게 귀속한다.
- 계정이 생긴 강아지는 시즌 모집단에 들어가며 현재 보유 0개여도 누적 점수를 유지한다.
- 총점은 `bonus × 36,000,000,000 + holding_units`의 정수 분자로 비교한다. 소수 표시를 반올림한 값으로 순위를 매기지 않는다.
- 동점 순위는 기존 계산처럼 `1,1,3`이며, 동점 표시 순서는 pet ID 기준으로 고정한다. ID 순서가 승자를 정하지 않는다.
- 부정행위 제외·운영 보정은 현재 구현되지 않았다. 적용 시 기존 결과를 몰래 수정하지 않고 제외/보정 규칙과 결과 revision을 별도 정의한다.

`held_site_ms`는 여러 장소의 보유 시간을 합한 값이다. 실제 산책 시간·연속 보유 시간·방문 횟수와
다르다. 현재 이 필드만으로 “가장 오래 산책한 강아지”, “한 장소를 가장 오래 지킨 강아지” 칭호를
수여할 수 없다. 그런 칭호를 채택하면 해당 근거를 별도로 수집·검증해야 한다.

### 3.2 현재 순위와 최종 순위

현재 순위는 한 `as_of_ms`까지 모든 대상 계정을 투영해 계산한다. 페이지마다 다른 시각으로
정산한 값을 섞지 않는다. `snapshot_id`에 시즌·규칙/경계 버전·기준 시각·정렬 결과를 고정하고
cursor는 그 snapshot에 묶는다. 현재 계정은 새 점령으로 변해도 다음 페이지는 같은 snapshot을 읽는다.

현재 점수 조회가 보너스 지급이나 계정 정산 쓰기를 일으키지 않는다. 랭킹용 snapshot/cache를
만드는 것과 점수 원장을 변경하는 것은 구분한다. 갱신 간격·만료 시간·페이지 크기는 부하 검증 후
정하며 임의의 초 단위를 이 문서에서 확정하지 않는다. snapshot 만료는 명시적인 재조회 응답이다.

시즌 종료 후 최종 순위는 봉인된 결과를 읽는다. 종료 시각은 지났지만 봉인이 끝나지 않았으면
`FINALIZING`이라는 **조회 상태 제안**으로 안내한다. 현재 DB의 시즌 enum에 이 상태가 있는 것은
아니다. 종료 시각까지 계산한 임시 성적을 확정 우승·칭호 수여로 표시하지 않는다.

## 4. 칭호 정책 — 제안 v0

### 4.1 먼저 검토할 최소 칭호

최초 구현 후보는 `neighborhood_champion` 하나다. 화면 문구 “동네 강자”는 예시이며 이름도
미확정이다. 칭호 종류를 늘리기 전에 수여·기록·공개·취소 흐름부터 완성하는 안이다.

| 항목 | 제안 v0 | 결정 상태 |
|---|---|---|
| 귀속 | 해당 season/scope의 pet | 제안 |
| 근거 | 봉인된 최종 순위 1위이며 정확한 총점이 0보다 큼 | 제안, 기존 합의 아님 |
| 공동 1위 | 조건을 충족한 전원 수여. ID 순서로 한 마리만 선택하지 않음 | 제안 |
| 참가자/승자 없음 | 수여 0건으로 작업 완료, 허위 수상자 생성 안 함 | 제안 |
| 수여 시각 | 시즌 종료 성적 봉인 후 서버 작업에서 처리 | 제안 |
| 칭호 보유 | 해당 시즌의 획득 기록은 다음 시즌 이후에도 유지 | 기록 보존 방향에 맞춘 제안 |
| 현재 챔피언 표현 | 과거 획득과 구분. 화면에 동네·시즌을 함께 표시 | 제안 |
| 대표 표시 | 보유자가 선택. 기본은 선택 없음, 소유 강아지의 유효한 award만 허용 | 제안 |
| 초기 점유 반영 시즌 | 소급 보너스 없음은 기존 코드. 칭호 수여 허용 여부는 미결 | 활성화 전에 결정 필요 |

“최대 영역 보유”, “꾸준한 산책”, “탈취왕”은 가능한 후속 아이디어일 뿐 이번 수여 목록이 아니다.
추가할 때는 근거 metric의 실제 의미, 최소 자격, 동점, 반복 교환 유인, 기존 부정행위 대응을
정해야 한다. 새로운 칭호가 새 점수를 지급하는지도 별도 정책이다. v0 제안은 칭호가 점수나
배율을 다시 올리지 않는 것으로 둔다.

### 4.2 획득과 현재 표시를 분리

`TitleAward`는 어떤 성적으로 언제 획득했는지를 보존한다. 다음 시즌 초기화로 삭제하지 않는다.
`TitleSelection`은 사용자가 현재 대표로 표시할 award ID다. 선택 해제는 수여 취소가 아니다.
칭호 보유가 공개 동의를 의미하지 않고, 이전 시즌 챔피언을 현재 시즌 1위로 표시하지 않는다.

현재 점유 지도는 현재 주인을 표시한다. 예전 주인이 해당 시즌 칭호를 받았더라도 장소 소유권을
복구하지 않는다. 공개 칭호·강아지 이름·사진은 조회 시점의 공개 설정을 따른다. 수여 원장의
과거 이름/사진 snapshot을 곧바로 다른 사용자에게 내보내는 구현은 피한다.

## 5. 수여 작업·멱등성·정정 계약 — 제안 v0

순위 봉인과 칭호 수여를 **별도 복구 가능한 서버 작업**으로 둔다. 칭호 실패가 점령/시즌 종료를
되돌리지 않는다. 대신 “시즌 종료됨”과 “칭호 수여 완료”를 별개 상태로 조회할 수 있어야 한다.

1. 시즌 시작 또는 수여 계획 생성 시 칭호 정책 version과 조건 snapshot을 고정한다. 재시도 때 최신 규칙으로 바꾸지 않는다.
2. 봉인된 결과와 그 결과 식별자/revision을 읽는다. 미봉인 결과에는 수여하지 않는다.
3. 해당 시즌 수여 작업을 잠그고, 동일 근거·정책으로 대상 집합을 계산한다.
4. `(season_id, scope_id, pet_id, title_code)` UNIQUE로 award를 저장한다. 정책 version은 근거 데이터이며 중복 지급을 피하기 위해 재실행마다 새 UNIQUE 키로 만들지 않는다.
5. 같은 transaction에서 수여 목록과 작업 완료 상태를 저장한다. 중간 실패는 그 묶음을 rollback한다.
6. 알림이 필요하면 commit 후 별도 전송하거나 같은 transaction의 outbox에 남긴다. 알림 실패로 재수여하지 않는다. 알림 기능 자체도 현재 미구현이다.

재실행 시 같은 UNIQUE 키의 award가 있으면 근거/정책 일치를 확인해 기존 결과를 반환한다.
내용이 다르면 조용히 덮어쓰지 않고 `award_identity_conflict`로 중단한다. 중도 실패·프로세스
재시작·시즌 수여 작업 두 개가 동시에 실행돼도 결과가 같아야 한다.

부정행위 판정·운영 오류로 취소가 필요하면 원본 award를 삭제하지 않고 `REVOKED` 사건을 추가한다.
권한 있는 운영 주체, 사유 코드, 원본 근거, 처리 시각, 고유 명령 ID를 보존한다. 복원은 별도
`RESTORED` 사건으로 기록한다. 현재 상태는 이 사건으로 계산한다. 일반 APP은 수여/취소/복원을
호출할 권한이 없다. 운영 도구와 사유 정책은 별도 구현 대상이다.

취소된 칭호가 대표로 선택돼 있으면 공개 projection에서 즉시 제외하고, 본인 화면에 취소 상태를
보여준다. 계정/반려견 삭제와 기록 익명화는 기존 DEV 삭제 흐름과 합의한 방식으로 처리한다.
기록 보존이 개인정보를 영구 공개한다는 의미는 아니다.

## 6. 추가할 저장 구조 — 제안, migration 미작성

아래 이름은 논리 모델이다. Geo Alembic 0033에는 **어느 것도 추가되어 있지 않다.**

| 구조 | 핵심 필드·제약 | 현재 기반과 관계 |
|---|---|---|
| `GameScope` | scope ID, 표시 이름, 경계 version, 경계 원본/장소 집합 근거 | 현재 문자열 scope_id를 실제 지역 정의에 연결 |
| `SeasonSiteMembership` | season/scope/site, 경계 version, 같은 시기 장소 한 scope | 현재 시즌별 site 집합의 귀속/변경 근거 확장 |
| `LeaderboardSnapshot` | snapshot ID, season/scope, as_of, 규칙/경계 version, 상태, 만료 | 현재 즉시 정렬만으로 부족한 일관된 페이지 조회 |
| `TitleDefinition` | 안정 title code, policy version, 표시 문구, 조건 snapshot | 수여 규칙과 번역/표시 문구를 구분 |
| `SeasonAwardRun` | season ID, 결과 revision, title policy snapshot, PENDING/COMPLETE 상태, 완료 시각 | 빈 수여 목록도 완료로 기록. 시즌 status와 별개 |
| `TitleAward` | award ID, season/scope/pet/title, policy version, 결과 근거, earned_at, UNIQUE 수여 키 | 기존 FinalStanding의 봉인 성적을 참조 |
| `TitleAwardEvent` | 고유 명령 ID, award ID, REVOKED/RESTORED, 사유·주체·시각 | 원본 지급과 취소/복원의 감사 근거 분리 |
| `TitleSelection` | pet ID, 선택한 award ID 또는 없음, revision | 회원 소유권·award 귀속/유효성 검사, 기대 revision 갱신 |
| `GamePublicProfile` | pet ID, 게임 공개 이름/사진/칭호 설정, revision | 기존 일반 반려견 프로필을 무조건 공개하지 않음 |

현재 결과 테이블에는 별도 결과 revision이 없다. 최초 버전을 고정하고, 봉인된 규칙·정렬된
성적의 식별자를 추가하는 방식부터 설계해야 한다. 대규모 snapshot 저장/만료/인덱스는 부하와
보존 정책에 맞춰 정한다. JSON으로 한 시즌 전체를 넣는 로컬 SQLite 방식으로 되돌리지 않는다.

## 7. DEV → APP HTTP 계약 — 미구현 제안

내부 Python 객체와 HTTP DTO를 분리한다. 제안 계약 버전 표기는 `territory-game.v1-draft`다.
실제 채택 시 version을 확정한다. 시각은 UTC epoch 정수 ms, 정확한 점수 분자는 십진 문자열,
ID는 서버 발급 문자열이다. 공개 응답에 다른 사용자의 session/claim/photo 원본 ID를 넣지 않는다.

### 7.1 제안 endpoint

| 경로 | 응답/권한 |
|---|---|
| `GET /app/territory/scopes?site_id=...` | 장소가 속한 동네와 활성 시즌. 위치를 보내는 별도 탐색 계약은 후속 |
| `GET /app/territory/seasons/{id}/leaderboard?cursor=...` | snapshot과 공개 가능한 순위 행. 인증된 게임 조회자 |
| `GET /app/territory/seasons/{id}/pets/{pet_id}/standing` | 본인 강아지 순위·점수. pet 소유권 검사 |
| `GET /app/territory/pets/{pet_id}/titles` | 본인: 전체 보유/취소 상태. 타인: 허용된 공개 projection만 |
| `PUT /app/territory/pets/{pet_id}/title-selection` | 본인 강아지의 award 선택/해제, expected_revision 사용 |

지급·봉인·현재 시각 변경 endpoint는 일반 APP에 만들지 않는다. public의 의미는 우선 게임을
조회하는 다른 사용자에 대한 공개이며, 인터넷 비로그인 공개는 별도 제품 결정이다.

### 7.2 랭킹 응답 예시

아래 값과 ID는 계약 설명용 샘플이다. 현재 서버 응답이 아니다.

```json
{
  "contract_version": "territory-game.v1-draft",
  "season_id": "season-example",
  "scope": {"id": "scope-example", "name": "샘플 동네", "boundary_version": "example-v1"},
  "snapshot_id": "snapshot-example",
  "as_of_ms": 1788652800000,
  "state": "FINALIZED",
  "point_denominator": "36000000000",
  "rows": [
    {"rank": 1, "public_pet": {"id": "pet-example", "name": "보리", "image_url": null},
     "total_units": "12240000000000", "selected_title": null}
  ],
  "next_cursor": null,
  "awards_state": "PENDING"
}
```

`state`는 순위 상태, `awards_state`는 수여 작업 상태다. FINALIZED이고 PENDING일 수 있다.
이때 APP은 “성적 확정 · 칭호 집계 중”을 표시하며 1위 행만 보고 칭호 획득을 생성하지 않는다.
cursor에는 snapshot ID와 안정된 위치를 묶고 다른 시즌/snapshot cursor는 거부한다.

### 7.3 칭호 응답·선택 예시

```json
{
  "award_id": "award-example",
  "title_code": "neighborhood_champion",
  "display_name": "동네 강자",
  "season_id": "season-example",
  "scope_id": "scope-example",
  "policy_version": "champion-proposal-v0",
  "earned_at_ms": 1788652800000,
  "status": "ACTIVE",
  "evidence": {"result_revision": "result-example", "rank": 1, "total_units": "12240000000000"}
}
```

이 예시는 본인 보유 내역용이다. 다른 사용자 응답에는 공개 정책이 허용한 필드만 남긴다.
대표 선택 요청은 `{"request_id":"selection-command-1","award_id":"award-example","expected_revision":0}`,
선택 해제는 `{"request_id":"selection-command-2","award_id":null,"expected_revision":1}` 형태를 제안한다.
APP은 응답 확인 전까지 원본 request ID·본문을 보관한다. 서버는 pet/request ID별 본문과 처리 결과를
같은 선택 transaction에 저장하고, 동일 재전송은 같은 결과를 반환한다. 같은 ID의 다른 본문은 거부한다.
새 명령의 expected revision이 다르면 충돌이다. 과거 명령 영수증을 재생했더라도 현재 대표 칭호는
최신 revision을 별도로 읽어 표시한다. 이 선택 명령 저장도 후속 migration에 포함해야 한다.

### 7.4 오류·오프라인·구버전

| 제안 코드/상태 | APP 처리 |
|---|---|
| `scope_unavailable`, 활성 시즌 없음 | 게임 미개설 안내. 동네를 임의 생성하지 않음 |
| `leaderboard_snapshot_expired` | 첫 페이지부터 새 snapshot 조회. 기존/새 행을 혼합하지 않음 |
| `season_finalizing`, 수여 PENDING | 확정 전/집계 중 안내. 승자·획득 애니메이션 보류 |
| `title_selection_changed` | 최신 선택 revision 조회, 임의 덮어쓰기 금지 |
| `title_not_owned`, `title_revoked` | 선택 실패 안내와 최신 보유 내역 갱신 |
| 비공개/권한 없음 | 계약상 허용한 미공개 상태. 숨겨진 이름·사진을 캐시에서 복원하지 않음 |
| 서버 미지원/기능 비활성 | 새 화면 준비 안 됨. 기본 점령 클라이언트와 분리 |

오프라인에는 마지막 조회 시각과 오래된 상태임을 표시한다. 점수 0·수여 실패로 단정하지 않는다.
계정 전환 시 이전 회원의 비공개 성적·선택 대기열이 새 화면으로 나오지 않아야 한다.

HTTP 상태 제안은 잘못된 cursor/입력 400, 미인증 401, 존재하지 않거나 해당 조회자에게 숨긴 자원
404, 선택 revision/identity 충돌 409, snapshot 만료 410, 서버 기능 미준비 503이다. 집계 중은
조회 자체의 실패가 아니므로 200과 상태 필드로 반환한다. 실제 채택 시 기존 DEV 오류 envelope와 맞춘다.

## 8. 공개와 순위 모집단 — 결정 필요

제안은 **점수/수여 계산과 공개 표시를 분리**하는 것이다. 비공개 강아지도 내부 성적과 본인
순위를 보존한다. 공개 목록에서 비공개 행을 제외하되 순위를 다시 매기지 않는 안을 검토한다.
이 경우 공개 목록에 1위가 없거나 `1,3,4`처럼 순위가 건너뛸 수 있다. APP은 이를 오류로 보지 않는다.
공개 동의한 강아지끼리만 별도의 순위를 계산하는 대안도 있으므로 D-06에서 반드시 선택한다.

공개 철회는 새 조회와 캐시 갱신에 반영하고, 성적/칭호 원장의 존재와 공개 이미지·이름을
분리한다. 기존 #260의 `owner_pet_name` 반환이 새 게임 공개 설정을 구현했다는 뜻은 아니다.
기존 응답을 어떻게 호환시킬지도 DEV/APP 계약에 포함한다.

## 10. 구현 작업과 완료 기준

| 단계 | 위치 | 산출물 | 검증해야 할 경우 |
|---|---|---|---|
| 정책 채택 | Geo 결정 문서 | D 항목의 채택안·근거·version | 초안 문구가 승인 사실로 바뀐 경위 추적 |
| 순수 계산 | Geo → DEV | 랭킹 모집단/칭호 대상 함수와 고정 fixture | 동점, 0점/빈 시즌, 부적격/초기 반영, 숫자 정확도 |
| scope 저장 | DEV | 경계 version·시즌 장소 매핑 migration | 경계 장소, 중복 귀속, 시즌 중 경계 갱신, 다중 동네 산책 |
| 랭킹 조회 | DEV | 일관된 snapshot, 본인/공개 API | 페이지 중 점수 변화, 만료, 비공개 행, 계정 전환 |
| 수여 저장/작업 | DEV | 정의·run·award·event migration, 재실행 워커 | 동시 수여, SQL 중간 실패, 빈 수여 완료, 근거 충돌 |
| 칭호 관리 | DEV | 취소/복원·선택·공개 projection | 남의 칭호 선택, 취소 후 표시, 응답 유실, 탈퇴 처리 |
| 제품 화면 | APP | 동네 선택, 현재/최종 순위, 보유/선택 칭호 | 시즌 구분, 집계 중, offline, 비공개, 구버전, 과거 우승 표현 |
| 통합 | DEV + APP | 실제 사진→점령→점수→봉인→수여→조회 시나리오 | 같은 사진/작업 재시도에도 점수·칭호 각각 한 번, 다음 시즌 뒤 기록 유지 |

칭호 완료는 “rank 1을 화면에 배지로 그렸다”가 아니다. 정책 version과 봉인 성적을 근거로
서버가 수여하고, 재시도·공개 변경·다음 시즌·취소/복원 뒤에도 일관되게 조회되는 상태다.
