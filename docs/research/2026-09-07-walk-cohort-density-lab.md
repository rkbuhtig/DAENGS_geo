# 산책 3·30·100회 UI 밀도 실험

> 이 문서는 Geo `185747f` 기반 로컬 실험의 당시 기록이다. 본문의 코드 경로·실행 명령·localhost 주소는 해당 실험 작업 공간을 가리킨다. 이 문서 PR에는 실험 실행 코드와 원천 캐시를 포함하지 않는다. [종합 보고서](2026-09-07-walk-diary-experiment-report.md)에서 최신 검토 결론과 이전 정책을 대체한 단계를, [보존 자료 안내](2026-09-07-walk-diary-evidence/README.md)에서 저장소만으로 확인할 수 있는 범위를 확인한다.

Geo 로컬 실험. 사용자가 승인한 부드러운 브러시를 유지하면서 기록이 쌓일 때의 지도·장면
탐색을 확인한다. 익숙함/새로움 판정, 차이 자동 강조, 서술 정책, Dev·App 이식은 범위 밖이다.

## 재현

```text
python -m tools.lab_server --tool walk-cohort --port 8766
http://127.0.0.1:8766/walk-cohort-lab?population=100
```

상단 `기존 예시 / 3회 / 30회 / 100회`로 전환한다. 기존 예시는 원래 8회 fixture와
계절·강수 필터를 유지한다. 밀도 실험은 같은 모집단의 앞 3/30/100회를 선택한다.
모두 2026년 9월의 합성 비 관측이며, 이 모집단에서 다른 계절·강수 조건은 빈 결과가 된다.
장면 수만 수기로 늘리지 않고 매 산책을 Geo 경로·paint·v2 생성기에 전달한다.

첫 세 경로는 반복 2회와 우회 1회다. 이후 일부는 크기·위치가 다른 합성 사각 경로를 따른다.
이것은 한 지역에서 제한된 경로군을 반복하는 UI 사례이며, 100개의 독립적인 실제 GPS 경로나
기기 잡음 모집단을 대표하지 않는다. 생성 결과는 로컬 프로세스 메모리에 캐시한다.

## 화면 변경

- 표시 농도는 기존 고정 density와 선택 산책 수 분모를 유지한다. 최대값에 맞춰 매번 색을
  늘리지 않는다. 같은 비율의 반복만 늘어나는 경우 색이 무조건 포화되는 구조가 아니다.
- 지도에서는 좌표 있는 모든 장면을 현재 줌의 투영 픽셀 거리(52px)로 묶는다. 겹치는 중심을
  다시 병합해 숫자 버튼이 포개지지 않게 한다. 위치 없는 장면은 여전히 목록에만 존재한다.
- 줌 변경은 표시 묶음만 재계산한다. 클릭한 장면 ID 집합을 보존하므로 확대 후에도 열어둔
  목록의 범위가 몰래 바뀌지 않는다. 그룹이 새 장소나 새 기록이 되는 것은 아니다.
- 시간순 목록은 페이지당 20개로 제한한다. 선택 카드의 이전/다음은 현재 범위 전체를 순회하며
  페이지 경계를 넘으면 목록의 페이지도 맞춘다.
- 모바일 카드 선택 시 지도가 보이는 위치로 이동하고, 화면 아래 카드에서 이전/다음 장면을
  확인한다. 선택한 점은 자기 숫자 묶음을 대신하고, 카드를 닫으면 그 묶음을 복구한다.
- 브러시 이미지는 현재 조회당 두 표현만 캐시한다. 장면 이동·줌 변경은 배경을 다시 계산하지
  않는다. UI JS를 별도 파일로 분리하되 명시적으로 선택한 lab에서만 제공한다.

## 관측 결과

Windows Edge headless, 1120×940 CSS px, 기본 zoom 17. 모두 실제 화면 캡처로 확인했다.

| 합성 산책 | 전체 장면 | 좌표 있는 장면 | 지도 표시 | 한 페이지 DOM 행 |
|---|---:|---:|---:|---:|
| 3회 | 24 | 18 | 6 | 20 |
| 30회 | 240 | 180 | 14 | 20 |
| 100회 | 800 | 600 | 14 | 20 |

100회에서는 zoom 14에 1개, zoom 19에 42개 표시였다. 위치 있는 장면 600개가 모든 줌에서
정확히 한 묶음에 포함되었고, 줌·장면 선택 후 결과 지문과 배경 이미지는 유지됐다.
기본 지도에서 반복된 경로의 모양이 남았으며, 성긴 경로는 더 연하게 보였다.

390×844 모바일 캡처에서 선택 후 지도는 y=71.5~401.5, 카드는 y=603.5~834에 있었다.
선택 점 y=236.5가 지도 안에 보이며 카드와 겹치지 않았다. 제목 줄바꿈과 선택 점을 가리던
숫자 묶음을 조정한 뒤 캡처를 다시 확인했다.

## 검증과 성능 한계

```text
pytest tests/spikes/test_walk_cohort_density.py tests/spikes/test_walk_cohort_lab.py -q
15 passed, 1 existing Starlette/httpx deprecation warning (28.34s)
ruff check scripts/spikes/walk_cohort/lab.py tests/spikes/test_walk_cohort_density.py tools/lab_server.py
All checks passed
```

브라우저: 3/30/100 전환, 좌표 장면 누락/중복 없음, 숫자 중심 간격, 줌 분리/병합,
줌 변경 중 목록 범위 유지, 시간순 페이지, 선택 카드와 지도 동시 노출, 다음 장면의 배경 불변,
카드 닫기 시 묶음 복구, 빈 결과 정리, 두 브러시 표현 전환, API 오류 시 기존 조건/결과 복구,
지도 라이브러리 실패 시 목록 유지, 320/360/430/760/1120px 가로 넘침 없음, JS 예외 없음.

첫 생성 포함 로드 시간은 3회 0.94s, 30회 6.87s, 100회 17.19s였다. 캐시된 산책으로 다시
조회한 100회는 약 1.8s, 응답 파싱 후 동기 UI JS 실행은 18~30ms였다. 이는 서버 fixture 생성과
로컬 응답 전송을 포함하는 관측이며 FPS/실기기 성능 보증이 아니다. 콜드 생성 비용, 전체 bundle과
장면을 함께 보내는 응답 크기, 실제 Android 프레임/메모리는 운영 이식 전에 따로 검토해야 한다.

전체 테스트 스위트는 실행하지 않았다. Dev·App에는 변경하지 않았다.
